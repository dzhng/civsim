## What changed

**`crates/sim/src/combat.rs:123-170`** — one record split into two, each with a single owner:

- `ScannedFriend { owner, offset: Vec2, distance, fighting, priority }` — what the scan holds while a friend can still be dropped. `record_friend` is unchanged apart from the type; selection never read an angle, so nothing about the cap or the mounted two-body dedup moves.
- `NearbyFriend { bearing, distance, fighting }` — what the three consumers read (blocked frontage, cover, swing obstruction). `owner`/`priority` are selection-only bookkeeping and are gone from the consumed record.
- `ScannedFriend::resolve()` computes `offset.y.atan2(offset.x)` — the same expression on the same inputs the eager code used, from the offset the scan captured (never a re-read of positions).

**`crates/sim/src/combat/targeting.rs:105, 149-156, 228-232`** — the scan fills `scanned`, storing `to` verbatim instead of `bearing()`. Past the `nearest < 0 || nearest_d > DISENGAGE_DIST` return, one `std::array::from_fn` maps the kept slots to resolved records, before the `blocked` check (so the disengaged path, which needs those bearings, still gets them). `friends_len`, slot order and every consumer expression are untouched. The enemy-side `bearing()` closure (rider wheel cost, strike candidates) is unchanged.

Choices I made and stand behind: two records rather than a lazy cell or a second bearing list (no parallel arrays, no cache across searches or ticks); resolution at exactly one point with `friends_len` still the single length; the consumed record trimmed to the three fields anyone reads.

## Hazards for root integration

- All three types are private to `crates/sim/src/combat`, so nothing outside the crate sees the change; but `record_friend`'s signature and the `NearbyFriend` field set both moved — any in-flight branch that touches `combat.rs`, `combat/targeting.rs` or `combat/resolution.rs` will conflict textually even though the semantics don't.
- The single remaining constraint to preserve in any future edit: the resolution point must stay *after* the no-target return and *before* the `blocked` check. Moving it earlier reintroduces the waste; moving it later strands the disengaged path.
- Adoption still needs root's same-build ABBA plus hashes 9000, 9300, 9308, 12000, 12308 and the 309 worker/direct ticks.
- Process note, not a code defect: restoring a test file with `mv file.bak file` preserves the old mtime, so cargo reran a stale binary and reported a phantom failure. Touch the file after any such restore.

# Candidate-only parallel target preparation

This is a bounded feasibility spike, independent of M1's renderer contracts. The
combined serial candidate did not clear its adoption rule. Keep that result and
all its code isolated; do not smuggle it into production as this spike's baseline.

Start from the retained candidate c8580623 only to explore a larger unchanged-
physics optimization. Move target geometry into one pure function, preserving
bucket order, caps/ties, original floating operations, prior-target selection and
body-snapshot inputs. Ordered completion must keep live friend fighting flags,
live target bearings and all combat/RNG writes in original soldier order.

Under the existing native-only parallel feature, prepare a fixed-size batch into
reused bounded scratch, then complete it in order. If an earlier impale moved the
searcher's live position, compare its bits and recompute through the same geometry
function. Verify every other prepared input's lifetime; do not assume the whole
Sim is immutable. The ordinary serial path calls the same function without batch
staging. No new user mode, WASM dependency, worker pool or toolchain is introduced.

Prove serial versus batched/parallel trajectories including output fields omitted
by state_hash. Include an impaled later actor, same-pass fighting, mounted bodies,
selection caps/ties, team identity and RNG/order; mutations must demonstrate the
position guard and live completion are load-bearing. Existing golden values and
mechanics assertions remain unchanged. Fixed storage must not grow with local
neighbor density, and no second target-search implementation survives.

Root measures only after correctness and review. Compare the native original,
new serial/one-thread overhead and a small fixed parallel configuration on the
same native workload. Inspect the existing profiler's setup/AI against the actual
canonical battle before claiming correspondence. Native gain is feasibility, not
WASM/browser speed or a universal timing floor. Any browser thread-pool port would
be a separate researched slice with canonical WASM parity and lifecycle proof.
Reject/reslice if staging/code complexity overwhelms useful progress; do not
repeat unchanged timing until it wins. No production adoption follows merely
from this native spike or from a passing mechanics test.
